These are the notes of Zeno 0.9.0 as far as it has come. It is not
released: this page is written as the work reaches `main`, and is
finished on the day of the release.

Zeno 0.9.0 is for code that is already written in another language.

**Another language's code in a `.zeno` file.** An `inline` block
holds C, Python or JavaScript as it was written, and the program
calls it:

```zeno
import c

let bits = inline c {
    #include <stdint.h>

    int ones(uint32_t x) {
        int count = 0;
        for (; x != 0; x &= x - 1) {
            count++;
        }
        return count;
    }
}

print(bits.ones(0xA5))
```

A block of C gives a library, as `c.library` does, with nothing
declared: the functions are typed from their own first lines, and
every call is checked before the program runs. `zeno run` builds the
block once and calls it. `zeno build`, in every build that writes C,
writes the block into the program's C, marked with the line of the
`.zeno` file it came from, so the built program calls it as C calls
C. Assembly goes inside a block of C, as the C compiler takes it, and
`c.library` now takes a file of assembly (`.s`, `.S`) beside the
files of C. `inline python` and `inline node` give a module of Python
and of Node, for `zeno run`.
[docs/inline.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/inline.md)
is the walkthrough, and chapter 61 of the decisions has the reasons:
why a block and not a superset of C, why a block ends where it does,
and why there is no `inline asm` and no `inline cpp`.

**A file of Python written again as Zeno.** `zeno convert shop.py`
writes `shop.zeno` and says what it did with each piece of the file:
written as Zeno, written with a `# convert:` comment where Zeno does
something a reader of Python would not expect, or kept as Python in an
`inline python` block that the Zeno calls. What it writes always runs
and prints what the Python printed, but for what the comments say.
The types come from the program itself, what is kept is kept for a
reason the report gives with its line, and what is written is read by
Zeno's own checker before it is given out. A program of 240 lines with
classes, dataclasses, dicts of objects, exceptions and f-strings is
written as Zeno but for its `import json`.
[docs/convert.md](https://github.com/zeno-src/zeno-lang/blob/main/docs/convert.md)
is the walkthrough, with what it writes for each thing in Python, what
it keeps and why, and what it does not promise; chapter 62 of the
decisions has the reasons. C is the next language it is to read.

**Everything new is asked for.** A block is asked for by the word
`inline` and by the `import` of its language, and `zeno convert` is a
command of its own. `inline` is not a
reserved word: `let inline = 3` means what it meant. A program with
no block is built into the same C, IR and bytecode as by 0.8.0, to
the byte: `tools/same.py` compared the two for every example, every
program of the tests of the targets, every sample of the book and
the benchmarks, fifteen ways each. Everything a program wrote for
0.8.0 means what it meant.
